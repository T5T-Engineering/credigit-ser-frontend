## 1. Design overview
Two layers, one seam:

- **`src/lib/api/`** — `config.ts` (`NEXT_PUBLIC_API_URL` → `apiEnabled`), `tokens.ts` (access token in memory, refresh
  token in `sessionStorage`), `client.ts` (`apiFetch` / `apiDownload`: Bearer, `X-Correlation-ID`, `Idempotency-Key`,
  RFC 9457 problems as `ApiProblem`, single-flight refresh on 401 / before expiry, sign-out on refresh failure).
- **`src/lib/iam/`** — the permission model: `permission-catalogue.json` + `permission-keys.ts` (generated by
  `scripts/sync-permissions.mjs` from the backend `config/permissions.json` and `config/roles.json`), `catalogue.ts`
  (catalogue, role default grants, protected patterns), `grants-store.ts` (demo: approved per-role grant / revoke deltas,
  `credigit.ser.iam`), `permissions.ts` (`useCan(key | keys)`, `usePermissionSet()`, `hasPermission()`,
  `actorHasPermission()`; API mode reads `/identity/me` permissions held in the session), `api.ts` (typed `/auth/*` and
  `/identity/*` calls).
- **`src/lib/auth/`** — `auth-config.ts` (`useAuthConfig()`: `GET /auth/config` in API mode; demo builds the same shape
  from rules + `NEXT_PUBLIC_AUTH_MODE`), `service.ts` (facade used by every auth page: `startSignIn`, `verifyChallenge`,
  `resendChallenge`, `forgotPassword`, `resetPassword`, `registerAccount`, `changeMyPassword`, `startStepUp`,
  `verifyStepUp`, `signOut`, `completeEntraSignIn` — dispatches to the API or to the demo `accounts.ts`), `accounts.ts`
  (demo accounts / challenges / lockout), `msal.ts` (MSAL initialised from the config response or env), `session.ts`
  (session store incl. `permissions`, `tenantId`, `authMode`).

The app shell mounts the library `PermissionProvider` with the effective permission set; `SideNav` gets `can` and each nav
item a `permission` list; `ModulePage` gates the page on the active tab's view key; buttons use `useCan(key)` from
`@/lib/iam/permissions` (typed `PermissionKey`, compile-time checked against the generated catalogue).

## 4. Data model
| Entity / store | Key fields |
|---|---|
| Session (`credigit.ser.session`, sessionStorage) | user { id, name, email, source }, roleId, roles, permissions (API mode), tenantId, authMode |
| Refresh token (`credigit.ser.refresh`, sessionStorage) | API mode only; access token in memory |
| API challenges (`credigit.ser.challenges`, sessionStorage) | challengeId, purpose, maskedEmail, codeLength, expiresAt, maxAttempts |
| Demo `Account` / `Challenge` (`credigit.ser.accounts`, localStorage) | as before; seeded users have no password unless `NEXT_PUBLIC_DEMO_PASSWORD` is set |
| Demo grants (`credigit.ser.iam`, localStorage) | `overrides: Record<roleId, { grant[], revoke[] }>` |

## 10. Gaps against the invariants
- API mode is built against the contract but not exercised by e2e (no backend in CI) — TD-970.
- Operations, notifications and every business module still use browser stores in API mode; only identity calls go to the
  backend (TD-971).
- Device binding / IP allow-list not enforced (AUTH-FR-11).
- Audit log is browser-side in demo mode.
